# Personal Finance Dashboard

개인 대출, 카드값, 고정지출, 생활비와 월별 부채 감소 흐름을 기록하고 확인하기 위한 개인용 재무 대시보드입니다.

DB나 관리자 페이지 없이 TypeScript 데이터 파일을 직접 수정하며, 월 1~2회 정도 실제 재무 상태를 갱신하는 것을 전제로 합니다.
데이터를 바꾸는 일은 곧 파일을 수정하고 commit 하는 일이므로, Git 이력이 그대로 재무 기록의 변경 이력이 됩니다.

## 프로젝트 목적

- 지금 총 대출 잔액이 얼마인지, 처음보다 얼마나 줄었는지 한눈에 확인합니다.
- 실제 부채 변화와 앞으로의 예상 부채를 같은 그래프에서 비교합니다.
- 특정 시점에 부채가 왜 늘거나 줄었는지 이벤트로 남겨, 나중에 돌아볼 수 있게 합니다.
- 사용자를 평가하거나 다그치는 앱이 아니라, 객관적으로 기록을 돌아보기 위한 도구를 지향합니다.
  그래서 숫자는 기본 색으로 두고, 감소는 연두색, 증가·신규 대출은 주황색으로만 구분합니다.

## 주요 기능

- 현재 총 대출 잔액, 카드 미결제 금액, 총 금융부담(대출 + 카드) 확인
- 최초 부채 대비 감소액 및 감소율 확인
- 월별 부채 변화 그래프 (실제는 실선, 예상은 점선, 신규 대출 시점 표시)
- 누적 원금 상환과 실제 순부채 감소의 차이 확인
- 신규 대출, 추가 상환, 완납, 조건 변경 등 이벤트 기록
- 대출별 잔액과 상환 진행률 확인
- 대출별 상세 화면: 이번 달 납입 예정(원금 + 이자), 잔액 추이, 월별 상환표
- 금융사 상환 일정표를 대출별 파일로 입력해 미래 납입 예상의 기준으로 사용
- 일정표가 입력되지 않은 달은 추정하지 않고 "미입력"으로 표시 (자동 계산 대출은 원금균등 / 원리금균등 / 만기일시 계산 사용)
- 전체 대출 월별 상환 계획, 대출별 납입 기여도
- 남은 원금, 앞으로 낼 예상 이자, 예상 총 상환액, 예상 완납월 계산
- 실제 기록과 예상치를 표·그래프에서 명확히 구분
- 카드값 및 고정지출 관리
- 월별 현금흐름 확인, 지난달 실제와 이번 달 예상 비교
- 3개월 / 6개월 / 12개월 후 예상 부채 확인
- 추가 상환 전략 시뮬레이터: 여유자금을 어느 대출에 넣으면 이자·완납·월 부담이 어떻게 바뀌는지 비교
- 라이트 / 다크 / 시스템 테마 지원
- PC / 태블릿 / 모바일 반응형 지원

### 페이지

| 경로 | 내용 |
| --- | --- |
| `/` | 대시보드 (요약, 부채 추이, 현금흐름, 대출 현황, 예상, 이벤트) |
| `/loans` | 남은 원금, 이번 달·다음 달 납입, 대출별 카드, 대출별 납입 기여도, 전체 월별 상환 계획 |
| `/loans/[id]` | 대출 하나의 상세 (이번 달 납입 예정, 잔액 추이, 원금·이자 그래프, 기본 정보, 월별 상환표) |
| `/strategy` | 추가 상환 전략 시뮬레이터 (이자 절감 / 월 부담 감소 / 완납기간 단축 / 균형 비교) |
| `/expenses` | 고정지출, 카드, 최근 카드 결제 내역 |
| `/history` | 월별 기록과 회고, 전체 이벤트 |

## 기술 스택

- Next.js 16 (App Router, React Compiler)
- React 19
- TypeScript
- Tailwind CSS 4
- Recharts (차트)
- Lucide React (아이콘)
- next-themes (라이트 / 다크 모드)
- ESLint

DB, 로그인, API Route, 외부 서비스 연동은 사용하지 않습니다. 모든 페이지는 빌드할 때 정적으로 생성됩니다.

## 실행 방법

Node.js 20 이상이 필요합니다.

```bash
npm install
npm run dev
```

브라우저에서 http://localhost:3000 을 열면 됩니다.

## 빌드 방법

```bash
npm run build   # 프로덕션 빌드
npm run start   # 빌드 결과를 로컬에서 실행
npm run lint    # ESLint 검사
```

데이터 파일에 오류가 있으면 `npm run build` 단계에서 에러 메시지와 함께 실패합니다.
예를 들어 존재하지 않는 대출 ID를 쓰거나, 월별 기록 중간에 빠진 달이 있으면 빌드가 멈춥니다.
데이터를 수정한 뒤에는 commit 하기 전에 꼭 빌드로 확인해주세요.

## 재무 데이터 수정 방법

재무 데이터는 모두 `src/data/` 폴더의 TypeScript 파일에 있습니다.
현재 들어 있는 값은 화면 확인용 샘플이므로, 실제 데이터로 교체해서 사용합니다.

| 파일 | 내용 | 수정 시점 |
| --- | --- | --- |
| `loans.ts` | 대출 목록과 상환 조건 (금리, 최초 대출금, 기록 시작 잔액, 시작일, 만기일, 상환 방식) | 대출이 새로 생기거나 조건이 바뀔 때 |
| `schedules/*.ts` | 금융사별 상환 일정표 (월별 예정 원금·이자) | 금융사 일정표를 받거나 바뀔 때 |
| `monthly-records.ts` | 월별 실제 기록 (수입, 대출별 원금·이자, 카드별 결제액, 생활비, 회고) | 매달 |
| `events.ts` | 신규 대출, 추가 상환, 완납, 조건 변경 등 이벤트 | 특별한 일이 있을 때 |
| `cards.ts` | 카드 목록, 이번 결제 예정액, 미결제 금액 (대출 아님) | 결제일·결제 후 |
| `fixed-expenses.ts` | 고정지출 항목 (적용 시작·종료 월 지정 가능) | 가끔 |
| `plan.ts` | 정기 상환과 별도로 계획한 추가 상환, 현금흐름 예상용 수입·생활비 (`null` = 미입력) | 계획이 바뀔 때 |
| `profile.ts` | 사이트 제목, 기록 시작 월(`trackingStartMonth`) | 거의 없음 |

### 처음 실제 데이터를 넣을 때

1. `profile.ts` 의 `trackingStartMonth`(기록 시작 월, 현재 `2026-10`)를 확인합니다.
2. `loans.ts` 에 대출 목록을 입력합니다.
   - `openingBalance` 에는 기록 시작 월 초 기준 잔액을 적습니다.
   - 기록을 시작하기 전부터 있던 대출은 `startedAt` 을 기록 시작 월보다 이전 날짜로 두거나, 모르면 `""` 로 비워 둡니다.
   - 아직 모르는 값은 비워 둡니다: `startedAt: ""`, `paymentDay: 0` 은 "미입력"으로 처리됩니다.
   - 계약 만기는 일자를 모르면 월만 `maturityMonth: "2029-05"` 형식으로 적습니다. 임의의 일자를 만들어 넣지 않습니다.
   - 상환 방식에 맞는 조건을 함께 입력합니다. (아래 "대출 상환 조건 입력하기" 참고)
3. `src/data/schedules/` 의 각 파일에 금융사 상환 일정표를 옮겨 적습니다. (아래 "금융사 상환 일정표 입력하기" 참고)
4. `cards.ts`, `fixed-expenses.ts` 에 카드와 고정지출 항목을 입력합니다.
5. `plan.ts` 에 계획된 추가 상환과 수입·생활비 가정을 입력합니다. 아직 모르면 `null` 로 두면 화면에 "미입력"으로 표시되고, 예상 잔액은 계산하지 않습니다.
6. 한 달이 끝나면 `monthly-records.ts` 에 기록 시작 월부터 월별 기록을 입력합니다.
7. 필요하면 `events.ts` 에 지금까지의 주요 이벤트를 남깁니다.

### 대출 상환 조건 입력하기

`loans.ts` 의 각 대출에는 아래 필드를 입력합니다. 현재 잔액은 입력하지 않습니다. 월별 기록의 원금 상환으로 자동 계산됩니다.

| 필드 | 의미 | 필수 |
| --- | --- | --- |
| `originalAmount` | 최초 대출금 | 필수 |
| `openingBalance` | 기록 시작 시점 잔액 (기록 전에 일부 갚았을 때만) | 선택 |
| `interestRate` | 현재 연 금리(%). 모르면 `null` (아래 참고) | 필수 |
| `variableRate` | 변동금리면 `true` (예상 이자에 안내 문구 표시) | 선택 |
| `repaymentType` | 상환 방식 (아래 표) | 필수 |
| `startedAt` | 대출 시작일 `YYYY-MM-DD` (모르면 `""`) | 선택 |
| `maturityMonth` | 계약상 만기 월 `YYYY-MM` (모르면 `""`) | 방식에 따라 |
| `paymentDay` | 월 납입일 (매월 n일, 모르면 `0`) | 선택 |
| `monthlyPrincipal` | 월 원금 상환액 | 방식에 따라 |
| `monthlyPayment` | 월 납입액. `equal-payment` 는 자동 계산에 사용, `manual` 은 화면의 "월 정기 납입" 참고값으로만 표시 | 선택 |
| `schedule` | 금융사 상환 일정표 (`schedules/` 파일에서 import) | 선택 |
| `firstPaymentMonth` | 1회차 납입 월 `YYYY-MM` (자동 계산 대출, `totalInstallments` 와 함께) | 선택 |
| `totalInstallments` | 총 상환 회차 | 선택 |
| `prepaymentFeeRate` | 중도상환수수료율(%). 생략하면 "수수료 정보 미입력" | 선택 |
| `prepaymentFeeEndMonth` | 중도상환수수료가 부과되는 마지막 월 `YYYY-MM` | 선택 |
| `prepaymentFeeAssumed` | 수수료율이 확인값이 아닌 가정값이면 `true` (화면에 "가정" 표시) | 선택 |
| `paidThroughMonth` | 이 달 납입분까지 `openingBalance` 에 반영됨 `YYYY-MM`. 예상 계산은 그다음 달부터 | 선택 |

| `repaymentType` | 의미 | 필요한 값 | 매달 계산 |
| --- | --- | --- | --- |
| `equal-principal` | 원금균등상환 | `monthlyPrincipal` 또는 `maturityMonth` | 원금 = 설정값, 없으면 남은 원금 ÷ 만기까지 남은 개월 수 |
| `equal-payment` | 원리금균등상환 | `monthlyPayment` 또는 `maturityMonth` | 납입액 = P×r×(1+r)ⁿ / ((1+r)ⁿ−1), 원금 = 납입액 − 이자 |
| `interest-only` | 만기일시상환 | `maturityMonth` | 매달 이자만, 만기 월에 원금 전액 |
| `manual` | 상환 일정표 | `schedule` | 일정표 값 그대로. 미입력 달과 일정표가 끝난 뒤는 **추정하지 않음** |

- `P` 는 그 달의 월초 원금, `r` 은 연 금리 ÷ 12, `n` 은 만기까지 남은 납입 횟수입니다.
  추가 상환이 있으면 다음 달부터 줄어든 원금으로 납입액을 다시 계산합니다. (`monthlyPayment` 를 직접 적었다면 그 금액을 유지)
- 자동 계산 대출은 만기 월이 되면 남은 원금을 모두 상환하는 것으로 계산합니다.

#### 일정표가 없는 대출: 자동 계산 (예: 다올·에큐온·OK저축은행, DB 신용대출)

금융사가 월별 상환 예정표를 주지 않는 대출은 `manual` 대신 실제 대출 조건으로 자동 계산합니다.

```ts
{
  id: "loan-daol",
  originalAmount: 3_000_000,
  openingBalance: 2_669_494,      // 10월 납입 후 잔액
  interestRate: 13.91,
  repaymentType: "equal-payment", // 원리금균등
  startedAt: "2026-07-01",        // 대출 실행일
  maturityMonth: "2028-07",       // 계약 만기
  firstPaymentMonth: "2026-08",   // 1회차 납입 월
  totalInstallments: 24,          // 총 24회 (2026-08 ~ 2028-07)
  paidThroughMonth: "2026-10",    // 10월(3회차)까지 납입 완료
  schedule: [],                   // 금융사 예정표 없음
}
```

- 남은 회차 = 총 회차 − 이미 지난 회차 (`firstPaymentMonth` + `totalInstallments` 가 있으면 만기월보다 우선)
- 1회차 월을 모르면 `firstPaymentMonth` 는 비워 둡니다. 이때는 `paidThroughMonth` 다음 달부터 계약 만기월까지를 남은 기간으로 계산합니다.
  예: DB 신용대출은 10월분까지 납입, 만기 2029년 1월 → 2026년 11월 ~ 2029년 1월 27회.
  과거 회차를 공식으로 재현하지 않고 **현재 실제 잔액(`openingBalance`)을 기준점**으로 미래만 계산합니다. (이 경우 회차 번호는 표시하지 않습니다)
- 월 납입액 = 남은 원금 기준 원리금균등 공식, 회차 번호는 상환표에 "4회차"처럼 표시합니다.
- 마지막 회차가 계약 만기보다 늦게 계산되면 경고합니다.
- `paidThroughMonth` 이전 달은 "납입 없음"으로 보고, 상세 화면에는 "다음 납부 · 2026년 11월 · 4회차"를 보여줍니다.
- `firstPaymentMonth` 이전 달도 "납입 없음"입니다. 예를 들어 에큐온저축은행(2026-09-29 실행, 1회차 2026-11, 총 48회)은
  아직 첫 납입 전이므로 `paidThroughMonth` 없이 두고, 상세 화면에 "다음 납부 · 2026년 11월 1일 · 1회차"를 보여줍니다.
  (`paymentDay` 를 입력하면 납부일까지 함께 표시합니다)
- 일할 이자, 첫 회차 기간, 원 단위 반올림 때문에 실제 청구액과 몇백~몇천 원 차이가 날 수 있으며, 화면에 "예상 계산 기준" 배지와 안내가 표시됩니다.
- 나중에 금융사 청구액을 알게 되면 `schedule` 에 그 달만 적어도 됩니다. 입력한 달은 자동 계산보다 우선합니다.

#### 계약 만기(`maturityMonth`)와 예상 완납은 다른 개념입니다

| | 계약 만기 | 예상 완납 |
| --- | --- | --- |
| 출처 | 금융사 계약 (`maturityMonth`) | 상환 일정표·실제 기록을 따라 계산 |
| `manual` 대출에서의 역할 | 표시와 일정표 검증에만 사용 (계산에 쓰지 않음) | 일정표가 원금 0원까지 입력된 경우에만 표시, 아니면 "일정표 미완성" |
| 자동 계산 대출에서의 역할 | 남은 납입 횟수 계산, 만기 월에 잔액 일괄 상환 | 자동 계산 결과 |

대출 상세 화면에는 **"계약 만기 2029년 5월"** 과 **"상환 일정표 기준 예상 완납"** 을 따로 표시합니다.

`manual` 대출은 계약 만기와 일정표를 비교해 아래 경우에 **경고**를 보여줍니다.
만기 연장이나 마지막 회차 조정이 있을 수 있으므로 빌드는 막지 않습니다.

- 일정표에 계약 만기월 이후 달이 들어 있는 경우
- 일정표가 계약 만기월까지 입력되어 있는데도 만기월에 원금이 남는 경우
  (1,000원 또는 잔액의 0.1% 중 큰 금액 이하의 차이는 마지막 회차 반올림으로 보고 경고하지 않습니다)

`maturityMonth` 가 `YYYY-MM` 형식이 아니면 빌드 에러가 납니다.
- 자동 계산은 `manual` 이 아닌 대출에서만 쓰입니다. 이 대출들은 일정표에 입력된 값이 있으면 그 값을 쓰고, 없으면 자동 계산합니다.
- `manual` 대출은 금융사 일정표가 유일한 기준입니다. 일정표에 없는 미래를 임의로 추정하지 않습니다.

### 금융사 상환 일정표 입력하기

실제 운영에서는 각 금융사가 제공하는 상환 일정표를 그대로 옮겨 적고, 이것을 미래 납입 예상의 기준으로 씁니다.
일정표는 대출마다 `src/data/schedules/` 아래 파일 하나로 관리합니다.

```text
src/data/schedules/
├─ korea-investment.ts   # 한국투자저축은행
├─ hanwha.ts             # 한화저축은행
└─ jeonbuk.ts            # 전북은행
```

다올저축은행, 에큐온저축은행, DB 신용대출, OK저축은행은 금융사가 월별 예정표를 주지 않아 일정표 파일 없이 원리금균등으로 자동 계산합니다.

신한카드처럼 카드대금 중 아직 결제되지 않은 금액은 대출이 아니므로 일정표를 만들지 않고 `cards.ts` 에서 관리합니다.
(아래 "카드 미결제 금액" 참고)

각 파일에는 월별 예정 원금과 이자를 적습니다. 총 납입액은 `principal + interest` 로 자동 계산되므로 적지 않습니다.

```ts
import type { ManualPayment } from "@/types/finance";

export const jeonbukSchedule: ManualPayment[] = [
  { month: "2026-11", installment: 11, principal: 67_566, interest: 43_555 },
  { month: "2026-12", installment: 12, principal: 68_242, interest: 42_879, paymentDate: "2026-12-10" },
  // ...
];
```

| 필드 | 의미 | 필수 |
| --- | --- | --- |
| `month` | 납입 월 `YYYY-MM` | 필수 |
| `principal` | 예정 원금. 아직 모르면 `null` | 필수 |
| `interest` | 예정 이자. 아직 모르면 `null` | 필수 |
| `installment` | 금융사 일정표의 회차 (화면에 "11회차"로 표시) | 선택 |
| `paymentDate` | 납부 예정일 `YYYY-MM-DD` | 선택 |
| `remainingPrincipal` | 일정표에 적힌 납입 후 잔액 (대조용, 계산에는 쓰지 않음) | 선택 |
| `note` | 메모 | 선택 |

`loans.ts` 에서는 일정표를 import 해서 연결하고, 상환 방식은 `manual` 로 둡니다.

```ts
import { hanwhaSchedule } from "./schedules/hanwha";

{
  id: "loan-hanwha",
  repaymentType: "manual",
  schedule: hanwhaSchedule,
  // ...
}
```

- **`null` 은 "아직 입력하지 않음", `0` 은 "실제로 0원"** 입니다.
  처음 만든 파일에는 2026년 10월부터 6개월치 빈 템플릿(`principal: null, interest: null`)이 들어 있습니다.
- 미입력(`null`) 달은 화면에 **"미입력"** 으로 표시하고 합계에서 뺍니다. 미입력 달이 있으면 그 뒤의 남은 원금은 **"미확정"** 으로 표시합니다.
- **예상 완납월**은 일정표를 따라갔을 때 원금이 미입력된 달 없이 남은 원금이 0원이 되는 달이 있을 때만 표시합니다.
  일정표 마지막 달을 완납월로 보지 않으며, 0원에 닿지 않으면 **"일정표 미완성"** 으로 표시합니다.
- 완납 월까지 빠짐없이 입력하면 이번 달 납입액, 월별 납입, 남은 원금, 잔여 이자, 대출별·전체 완납월이 모두 채워집니다.
- **일정표 첫 달보다 앞선 달은 납입이 없는 것으로 봅니다.** 예를 들어 전북은행 일정표가 2026년 11월(11회차)부터 시작하면,
  2026년 10월은 "미입력"이 아니라 "이번 달 납입 없음"으로 보고 상세 화면에 **"다음 납부 · 2026년 11월 · 11회차"** 를 보여줍니다.
  따라서 일정표는 반드시 다음 납부 회차부터 빠짐없이 적어주세요.
- 대출 상세 화면에는 **"금융사 상환 일정표 기준"** 또는 **"예상 계산 기준"** 표시가 붙고,
  상환표의 각 행에도 "일정표" 표시가 붙어 실제 일정표와 자동 예상치를 구분할 수 있습니다.

빌드할 때 일정표를 검사하고, 문제가 있으면 `npm run build` 가 에러 메시지와 함께 멈춥니다.

- 같은 달이 두 번 있는 경우
- 월 순서가 뒤바뀐 경우
- `principal` 또는 `interest` 가 음수인 경우
- `installment`(회차)가 이전 달보다 커지지 않는 경우
- 이번 달 이후 일정표의 원금 합계가 현재 잔액보다 많은 경우
  (금융사 반올림을 고려해 1,000원 또는 잔액의 0.1% 중 큰 금액까지는 허용합니다)

#### `monthly-records.ts` 와 일정표의 차이

| | `monthly-records.ts` | `schedules/*.ts` |
| --- | --- | --- |
| 내용 | 실제로 납입한 금액 | 앞으로 납입할 예정 금액 |
| 화면 표시 | "실제" | "예상" (금융사 상환 일정표 기준) |
| 작성 시점 | 한 달이 끝난 뒤 | 금융사 일정표를 받았을 때 |

같은 달에 둘 다 있으면 실제 기록이 우선합니다. 따라서 납입이 끝난 달의 일정표 항목은 그대로 두어도, 지워도 됩니다.

#### 우선순위

같은 달의 값은 상환 방식에 따라 아래 순서로 하나만 사용합니다.

| 상환 방식 | 1순위 | 2순위 | 3순위 |
| --- | --- | --- | --- |
| `manual` | 실제 기록 (`monthly-records.ts`) | 금융사 상환 일정표 | **미입력 / 계산할 수 없음** (추정하지 않음) |
| `equal-payment` · `equal-principal` · `interest-only` | 실제 기록 | 일정표에 입력된 값 (덮어쓰기) | 자동 계산 |

`plan.ts` 의 추가 상환은 2·3순위 값 위에 더해집니다.

#### 금리가 불명확한 대출: `interestRate: null`

금리가 자주 바뀌거나 일정하지 않아 금리를 관리하지 않는 대출은 `interestRate: null` 로 둡니다.
`0` 은 실제 무이자(0%)로 계산되므로, 금리를 모를 때는 `0` 대신 반드시 `null` 을 씁니다.

```ts
{
  id: "loan-example",
  interestRate: null, // 금리 정보 없음 (0% 아님)
  repaymentType: "manual",
  schedule: exampleSchedule,
  // ...
}
```

- 화면에는 금리 대신 **"금리 정보 없음"** 이 표시됩니다.
- 이자는 일정표에 적힌 값만 사용합니다. (`manual` 대출은 원래 일정표 밖을 추정하지 않으므로 금리가 없어도 계산에 영향이 없습니다)
- 금리를 모르면 자동 계산을 할 수 없으므로, `interestRate: null` 은 `repaymentType: "manual"` 과 함께만 쓸 수 있습니다.
  (다른 방식과 함께 쓰면 빌드 에러)

### 카드 미결제 금액

카드대금 중 아직 결제되지 않은 금액(할부 잔액 등)은 **대출이 아니므로** `loans.ts` 가 아니라 `cards.ts` 에 적습니다.

```ts
{
  id: "shinhan-card",
  name: "신한카드",
  issuer: "신한카드",

  originalUsedAmount: 3_740_000, // 처음 이용금액
  outstandingBalance: 2_529_600, // 아직 결제되지 않은 금액

  paymentDay: 27,                // 결제일 (매월 n일)
  currentPayment: 777_074,       // 이번 결제일에 낼 금액
}
```

| 필드 | 의미 | 필수 |
| --- | --- | --- |
| `paymentDay` | 결제일 (매월 n일) | 필수 |
| `currentPayment` | 이번 결제 예정액 | 선택 |
| `expectedMonthly` | 계획에 쓰는 월 예상 결제액 (생략하면 `currentPayment` 사용) | 선택 |
| `originalUsedAmount` | 처음 이용금액 | 선택 |
| `outstandingBalance` | 미결제 금액 | 선택 |

- 대시보드에는 **총 대출 잔액**, **카드 미결제 금액**, **총 금융부담(= 대출 잔액 + 카드 미결제 금액)** 을 따로 보여줍니다.
- 대출 상환률, 예상 완납월, 잔여 이자 계산에는 카드 미결제 금액을 **포함하지 않습니다**.
- 결제가 끝날 때마다 `outstandingBalance` 와 다음 `currentPayment` 를 갱신합니다.

### 추가 상환 전략 시뮬레이터 (`/strategy`)

여유자금을 **한 대출에 전액** 추가 상환한다고 가정하고, 대출별 결과를 나란히 비교합니다.
어떤 대출을 갚으라고 추천하지 않으며, 계산 결과를 비교하는 도구입니다.

- 금액을 직접 입력하거나 50만 / 100만 / 200만 / 300만원 버튼으로 고릅니다.
- 추가 상환 후 처리 방식을 고릅니다. (실제 방식은 금융사마다 다르므로 확인 필요)
  - **기간 단축**: 월 납입은 그대로 두고 완납을 앞당김
  - **월 납입 감소**: 만기는 그대로 두고 월 납입을 줄임
- 대출별로 현재 원금, 추가 상환 후 원금, 예상 완납월 변화(단축 개월 수), 잔여 이자 변화, 예상 이자 절감,
  월 납입 변화, 월 부담이 줄어드는 시점, 향후 24개월 납입 감소액, 중도상환수수료를 보여줍니다.
- 비교 기준
  - **이자 절감 기준**: 이자 절감액(수수료 정보가 있으면 수수료 차감) 순
  - **월 부담 감소 기준**: 월 납입이 더 빨리 줄어들거나 사라지는 순 (같은 시점이면 감소액 순)
  - **완납기간 단축 기준**: 단축 개월 수 순
  - **균형 비교**: 이자 절감 · 기간 단축 · 향후 24개월 납입 감소를 후보 중 최댓값 대비 비율로 바꿔 평균한 비교 지수 (추천 순위 아님)
- 카드의 "전체 효과 보기"를 누르면 그 전략을 적용했을 때 전체 남은 원금, 전체 잔여 이자, 전체 예상 완납월,
  월 납입액 변화, 이자 절감, 전체 완납기간 단축을 보여줍니다.

계산 방식

- 자동 계산 대출: 기존 스케줄 계산기에 "추가 상환 후 잔액"을 넣어 다시 계산합니다.
  기간 단축은 지금 월 납입액을 고정하고, 월 납입 감소는 남은 기간으로 월 납입을 다시 계산합니다.
- `manual` 대출: 금융사 일정표가 완납까지 입력된 경우에만 추정합니다 ("일정표 기준 추정" 표시).
  기간 단축은 일정표 납입액을 유지한다고 보고 기존/변경 후를 같은 방식으로 계산해 차이만 반영하고,
  월 납입 감소는 남은 회차의 원금·이자가 잔액 비율만큼 줄어든다고 봅니다.
  일정표가 완납까지 입력되지 않았으면 **"일정표 미완성으로 정확한 계산 불가"** 로 표시합니다.
- 중도상환수수료는 `추가 상환 금액 × prepaymentFeeRate%` 로 단순 계산하고, `prepaymentFeeEndMonth` 가 지났으면 0원입니다.
  수수료 정보가 없으면 **"수수료 정보 미입력"** 과 함께 **"중도상환수수료는 반영되지 않은 결과입니다."** 를 표시합니다.
- 현재 데이터는 금융사 확인 전이라 모든 대출에 **2% 가정**(`prepaymentFeeAssumed: true`)을 넣어 두었습니다.
  면제 기간은 실행 후 3년으로 보고, 실행일을 모르는 대출은 면제 종료월 없이 항상 적용합니다.
  실제 수수료율이나 남은 기간에 따라 줄어드는 방식이 확인되면 각 대출의 값을 바꿔주세요.
- 추가 상환 금액이 잔액보다 크면 잔액까지만 반영하고 남는 금액을 따로 보여줍니다.

### 계산 규칙

합계나 잔액처럼 계산할 수 있는 값은 데이터 파일에 저장하지 않고 `src/lib/` 에서 계산합니다.

- 최초 부채 = 기록 시작 월보다 먼저 실행된(또는 실행일 미입력) 대출들의 `openingBalance` 합계
- 기록 시작 월 **이후** 실행된 대출은 그 달의 "신규 대출"로 집계됩니다.
- 대출별 현재 잔액 = 기록 시작 잔액(또는 실행 금액) + 추가 인출 − 누적 원금 상환
- 순부채 감소 = 누적 원금 상환 − 누적 신규 대출 = 최초 부채 − 현재 부채
- 고정지출은 월별 기록에 `fixedExpenses` 를 적지 않으면 `fixed-expenses.ts` 기준으로 자동 계산됩니다.
- "이번 달"은 오늘 날짜가 아니라 **마지막 월별 기록의 다음 달**이고, 월별 기록이 없으면 기록 시작 월입니다.
  예를 들어 `monthly-records.ts` 가 2026년 10월까지 있으면 10월까지는 "실제", 11월부터는 "예상"으로 표시됩니다.
- 같은 달의 값이 여러 곳에 있으면 **실제 기록 → 금융사 상환 일정표 → (manual 은 미입력 / 그 외는 자동 계산)** 순서로 사용합니다.
- (자동 계산 대출) 예상 이자 = 월초 원금 × 연 금리 ÷ 12 (원 단위 반올림). 실제 금융사의 일할 계산, 납부일, 윤년, 중도상환 등과 차이가 있을 수 있습니다.
- 앞으로 낼 이자 = 이번 달부터 완납까지 대출별 이자의 합계.
  완납까지의 일정표가 모두 입력된 경우에만 표시하고, 그렇지 않으면 **"일정표 미완성"** 으로 표시합니다.
  이때 입력된 구간의 이자 합계는 **"입력된 일정표 기준 이자"** 로 따로 보여줍니다.
- 예상 총 상환액 = 남은 원금 + 앞으로 낼 이자 (위와 같은 조건에서만 표시, 아니면 "계산할 수 없음")
- 예상 완납월 = 원금 미입력 없이 남은 원금이 0원이 되는 달. 그 뒤로는 원금·이자 모두 0이며 월 납입 합계에서 빠집니다.
- 전체 예상 완납월 = 모든 대출의 완납월이 확인된 경우에만 그중 가장 늦은 달. 하나라도 확인되지 않으면 **"계산할 수 없음"**.
- 이번 달 현금흐름의 예상 잔액은 수입·생활비(`plan.ts`)와 모든 대출의 이번 달 일정표가 입력된 경우에만 계산합니다.

## 월별 데이터 갱신 방법

한 달이 끝나고 카드값과 대출 납입이 모두 확정되면 아래 순서로 갱신합니다.

1. `src/data/monthly-records.ts` 맨 아래에 지난달 기록을 추가합니다.
   첫 기록은 `trackingStartMonth`(2026-10)이어야 하고, 월은 빠짐없이 이어져야 합니다. (예: `2026-10` 다음은 반드시 `2026-11`)

   ```ts
   {
     month: "2026-10",
     income: 4_800_000,
     loanPayments: {
       "loan-korea-investment": { principal: 412_000, interest: 198_000 },
       "loan-hanwha": { principal: 312_450, interest: 105_250 },
     },
     cardPayments: { "shinhan-card": 777_074, "card-sub": 240_000 },
     livingExpenses: 300_000,
     review: "이번 달 한 줄 회고",
   },
   ```

   - `loanPayments` 의 키는 `loans.ts` 의 대출 `id`, `cardPayments` 의 키는 `cards.ts` 의 카드 `id` 입니다.
   - 마이너스통장처럼 기존 대출에서 추가로 빌린 금액은 `borrowed` 에 적습니다.
2. 신규 대출이 생겼다면 `loans.ts` 에 대출을 추가합니다. (`startedAt` 을 실행한 날짜로 설정)
3. 추가 상환, 완납, 금리 변경 같은 일이 있었다면 `events.ts` 에 이벤트를 추가합니다.
4. 금융사에서 새 상환 일정표를 받았다면 `src/data/schedules/` 의 해당 파일을 고칩니다.
   금리, 만기 등 조건이 바뀌었다면 `loans.ts` 를 수정합니다.
   이미 지난달이 된 일정표 항목은 지워도 됩니다. (지난달은 실제 기록이 우선합니다)
5. 추가 상환 계획이 바뀌었다면 `plan.ts` 의 `extraRepayments` 를 수정합니다.
6. `npm run build` 로 오류가 없는지 확인합니다.
7. commit 합니다. commit 메시지에 어떤 달의 기록인지 남겨두면 나중에 찾기 쉽습니다.

   ```bash
   git add src/data
   git commit -m "data: 2026년 10월 기록 추가"
   ```

## 배포 관련 메모

- 모든 페이지가 정적 페이지로 빌드되므로 Vercel 에 저장소를 연결하면 별도 설정 없이 배포됩니다.
  commit 을 push 할 때마다 자동으로 다시 빌드됩니다.
- GitHub Pages 처럼 정적 파일만 올리는 호스팅을 쓰려면 `next.config.ts` 에 `output: "export"` 를 추가하고,
  빌드 결과인 `out/` 폴더를 배포합니다. (하위 경로에 배포한다면 `basePath` 설정도 필요합니다.)
- **개인정보 주의:** 재무 데이터가 소스 코드에 그대로 들어 있습니다.
  - GitHub 저장소는 반드시 **Private** 으로 유지해주세요.
  - 배포한 사이트도 누구나 볼 수 있으므로, Vercel 의 Deployment Protection(비밀번호/로그인 보호) 등을 켜두는 것을 권장합니다.
  - 검색 엔진 노출을 막기 위해 페이지에 `noindex` 설정이 들어 있지만, 이것만으로 접근을 막을 수는 없습니다.
- 로컬에서만 볼 생각이라면 배포 없이 `npm run build && npm run start` 로 충분합니다.
